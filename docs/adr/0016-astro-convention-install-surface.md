# Astro install surface is convention-first

Consumer Astro hosts should opt in with `cms()` and project files beside Astro’s
own config — not by wiring a host factory and path options in `astro.config`.

**Happy path**

- `integrations: [svelte(), cms()]` — **zero options**
- `src/cms.config.ts` — human-authored CMS unified tree (schema + UI + Svelte
  bindings) + preview URL map ([ADR-0019](0019-cms-first-semantic-schema.md))
- `src/content.config.ts` — **generated** native Astro collections (committed;
  regenerated by `cms()`; CI `cms generate --check`)
- Content entries under `src/content/` (Astro’s conventional content root)

`cms()` requires `src/cms.config.ts` (hard-fail in `astro:config:setup` if
missing). It always installs one bundle: generate `content.config`, inject
`/cms`, wire the package default `CmsHost` (built-in FS adapter from compiled
IR), and mount `/_cms`.

`@cms/astro` builds that default `CmsHost` from editor configuration /
compiled IR ([ADR-0019](0019-cms-first-semantic-schema.md),
[ADR-0020](0020-ir-form-model-only-editor-configuration.md)), write-back root
`src/content`, allowlist from IR collection bases, and `nodeFsWriter`. Projects
do not ship `createHost` unless they replace the adapter.

**Not collapsed**

- Browser editor config and server `content.config` stay separate module-graph
  edges ([ADR-0004](0004-live-content-config-discovery.md), ADR-0008), produced
  from one human `cms.config` source.

**Escapes (not on `cms()`)**

- Fixtures / non-convention layouts: `cmsHarness` from `@cms/astro/testing`
- Protocol-only / custom adapter: `createCmsMiddleware` (+ optional project
  `createHost`)

Virtual module IDs (`virtual:@cms/*`) are package-internal implementation.

**Why**

The reference host must look like a real consumer. An options matrix
(`editorConfig` vs `schemaPartition`, soft host-off flags) taught a mode story
after ADR-0019 already chose one default. Escapes stay available; they are not
the install face.
