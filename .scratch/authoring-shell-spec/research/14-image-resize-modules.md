# Image resize / WebP / srcset modules

**Ticket:** [Rich image field](../issues/14-rich-image-field.md)  
**Question:** Which existing modules can perform authoring-time image conversion and width generation for an Astro + Bun CMS route that writes a canonical WebP plus derivative files beside content, while YAML keeps one canonical path?  
**Product frame:** This note evaluates transform engines and Astro APIs; it does **not** choose widths, naming, overwrite rules, canonical-file semantics, or a persisted field shape. The current `Writer` is text-only (`readText` / `writeText`) ([source](../../../packages/crud/src/types.ts)); binary upload and binary writer operations remain separate work.

## Verdict

1. **`sharp` is the strongest direct server-side candidate.** Its own documentation explicitly supports Node.js, Deno, and Bun through Node-API v9; it accepts buffers or paths, resizes, encodes WebP, and writes named files with one short pipeline ([overview](https://sharp.pixelplumbing.com/), [install](https://sharp.pixelplumbing.com/install/), [resize](https://sharp.pixelplumbing.com/api-resize/), [WebP output](https://sharp.pixelplumbing.com/api-output/#webp)). Astro already uses a Sharp-backed local image service by default, and Astro 5.13.5 carries Sharp as an optional dependency ([Astro images](https://docs.astro.build/en/guides/images/#default-image-service), [Astro 5.13.5 package](https://github.com/withastro/astro/blob/astro%405.13.5/packages/astro/package.json)).
2. **Astro's configured local image-service `transform()` is a supported reuse seam, but `getImage()` alone is not an authoring-file API.** Astro documents calling `getConfiguredImageService()`, `parseURL()`, and `transform()` from a custom API endpoint; `transform()` returns image bytes. A `/_cms` route could persist those bytes itself, but Astro's documented output behavior is `dist/_astro` at static build or bytes from `/_image` in dev/on-demand rendering—not stable derivative files beside source content ([Astro v5 Image Service API](https://v5.docs.astro.build/en/reference/image-service-reference/), [built-in endpoint source](https://github.com/withastro/astro/blob/main/packages/astro/src/assets/endpoint/generic.ts)).
3. **`wasm-vips` is the most complete pure-Wasm server alternative for Node/Deno, but not yet a safe Bun assumption.** It exposes libvips in WebAssembly, documents Node and Deno imports, and can resize/encode via `thumbnailBuffer(...).writeToBuffer(".webp")`; however, its README calls the library early-development, and the latest owner report in the open Bun-support issue says Bun 1.3.5 failed with memory errors ([README](https://github.com/kleisauke/wasm-vips/blob/master/README.md), [efficient thumbnail example](https://github.com/kleisauke/wasm-vips/issues/75#issuecomment-2566948407), [Bun issue](https://github.com/kleisauke/wasm-vips/issues/108)).
4. **`@jsquash/*` is viable primarily as the browser/Web Worker path, not as the preferred Bun server engine.** The project provides separate decode, resize, and WebP encode packages and has a working Deno example, but its README labels Node support limited, experimental, and unoptimized; the Node example manually reads and compiles codec Wasm files ([project README](https://github.com/jamsinclair/jSquash/blob/main/README.md), [Node example](https://github.com/jamsinclair/jSquash/blob/main/examples/with-node/index.js), [Deno example](https://github.com/jamsinclair/jSquash/blob/main/examples/with-deno/index.js)).
5. **Do not start new work on `@squoosh/lib` or `@squoosh/cli`.** Their owning project explicitly marked both unmaintained and then removed them from the repository in 2023 ([lib README at retirement commit](https://github.com/GoogleChromeLabs/squoosh/blob/918c596cba36a46ff3d7aa8ffd69580bd22528e2/libsquoosh/README.md), [CLI README](https://github.com/GoogleChromeLabs/squoosh/blob/918c596cba36a46ff3d7aa8ffd69580bd22528e2/cli/README.md), [removal PR](https://github.com/GoogleChromeLabs/squoosh/pull/1321)).

## Findings

### 1. `sharp`: direct server implementation

- Sharp describes its primary use case as converting large images into smaller WebP/AVIF/JPEG/PNG outputs of varying dimensions. It accepts paths, `Buffer`, `ArrayBuffer`, and typed arrays as input ([overview](https://sharp.pixelplumbing.com/), [constructor](https://sharp.pixelplumbing.com/api-constructor/)).
- Its resize API preserves aspect ratio when only a width is supplied; `withoutEnlargement: true` prevents upscaling. Only one resize operation applies per Sharp pipeline, so multiple widths require separate pipelines (or clones) and outputs ([resize API](https://sharp.pixelplumbing.com/api-resize/)).
- WebP output is first-class: `.webp({ quality, lossless, nearLossless, effort, ... })` followed by `.toBuffer()` or `.toFile()` ([WebP options](https://sharp.pixelplumbing.com/api-output/#webp)). A typical width loop is therefore structurally:

  ```ts
  await Promise.all(
    widths.map((width) =>
      sharp(inputBytes)
        .rotate()
        .resize({ width, withoutEnlargement: true })
        .webp({ quality })
        .toFile(fileFor(width)),
    ),
  );
  ```

  This illustrates the library call shape only; `widths`, `quality`, and `fileFor()` are CMS policy still to grill. Astro's own Sharp service also rotates for EXIF orientation, resizes, selects WebP, and returns a buffer ([Astro 5.13.5 Sharp service source](https://github.com/withastro/astro/blob/astro%405.13.5/packages/astro/src/assets/services/sharp.ts)).
- Bun: Sharp's official install page says `bun add sharp`; Bun supports Node-API addons and includes `sharp` as an example of a dependency whose lifecycle scripts may need trust when a project replaces Bun's default trusted list ([Sharp install](https://sharp.pixelplumbing.com/install/), [Bun Node-API](https://bun.sh/docs/runtime/node-api), [Bun lifecycle scripts](https://bun.sh/docs/pm/lifecycle)).
- Deno: Sharp's install page gives `deno add --quiet npm:sharp` and runtime permissions `--allow-env --allow-ffi --allow-read --allow-sys`; Deno's own image example imports `npm:sharp`, resizes, converts to WebP, and writes with `toFile()` ([Sharp install](https://sharp.pixelplumbing.com/install/), [Deno example](https://docs.deno.com/examples/resize_images/)). Deno's Node compatibility docs require local `node_modules` and `--allow-ffi` for native Node-API addons ([Deno Node/npm compatibility](https://docs.deno.com/runtime/fundamentals/node/#node-api-addons)).
- Install friction is bounded but real: Sharp publishes prebuilt binaries for common OS/CPU/libc combinations; cross-platform lockfiles and less-common targets require package-manager/platform care, while source builds require a C++17 toolchain, `node-gyp`, and compatible libvips ([install](https://sharp.pixelplumbing.com/install/)).
- Sharp also ships an optional Wasm package, but its official restrictions say browsers and single-threaded environments are unsupported. It is therefore **not** the browser-Wasm option being sought here ([Sharp WebAssembly install notes](https://sharp.pixelplumbing.com/install/#webassembly)).

### 2. How Astro uses Sharp, and what can be reused

- Sharp is Astro's default `astro:assets` image service. Astro 5.13.5 lists `sharp` as an optional dependency (`^0.33.3`), and the current workspace targets Astro `^5.13.0` ([Astro images](https://docs.astro.build/en/guides/images/#default-image-service), [Astro package source](https://github.com/withastro/astro/blob/astro%405.13.5/packages/astro/package.json), [workspace package](../../../package.json)).
- Astro's Sharp service takes an input `Uint8Array`, auto-orients via `rotate()`, resizes, converts to the requested format, and returns `{ data, format }` from `toBuffer()` ([Astro 5.13.5 source](https://github.com/withastro/astro/blob/astro%405.13.5/packages/astro/src/assets/services/sharp.ts)). That is the same pixel-operation class needed by authoring generation, but Astro's service wraps it in delivery/build semantics.
- `getImage()` is documented for use in an API route and can return `srcSet.values` / an attribute string when supplied widths or densities. In development, those are URLs routed through the image service endpoint; at static build, transformed files go to hashed `dist/_astro` output ([`getImage()` reference](https://v5.docs.astro.build/en/reference/modules/astro-assets/#getimage), [v5 Image Service API](https://v5.docs.astro.build/en/reference/image-service-reference/)). This does not, by itself, produce stable beside-content filenames.
- The stronger Astro-first hook is the documented custom-endpoint path: obtain the configured service with `getConfiguredImageService()`, parse transform options, call its `transform()` method, and receive `Uint8Array` data ([v5 Image Service API](https://v5.docs.astro.build/en/reference/image-service-reference/)). A `/_cms` POST route can, as application code, loop widths and persist each returned `data`; Astro documents the call and byte return, while **the disk write, naming, atomicity, and cleanup remain CMS responsibilities**.
- Directly importing `sharp` still has the smallest surface for authoring-only files. Reusing Astro's service couples authoring behavior to whichever image service the host configures; that could be useful or undesirable, and is a grill choice rather than a research conclusion. Because Sharp is optional in Astro and Astro documents missing-install cases, a CMS package that imports Sharp directly should not assume Astro's transitive optional install is present ([Astro missing-Sharp error](https://docs.astro.build/en/reference/errors/missing-sharp/), [Astro package source](https://github.com/withastro/astro/blob/astro%405.13.5/packages/astro/package.json)).

### 3. `@jsquash/*`: browser Wasm and limited server use

- jSquash is a collection of ESM Wasm codecs derived from Squoosh and explicitly focused on browser and Web Worker environments. It separates format codecs from transforms: `@jsquash/jpeg` / `png` decode bytes to `ImageData`, `@jsquash/resize` transforms `ImageData`, and `@jsquash/webp` encodes `ImageData` to an `ArrayBuffer` ([project README](https://github.com/jamsinclair/jSquash/blob/main/README.md), [resize](https://github.com/jamsinclair/jSquash/blob/main/packages/resize/README.md), [WebP](https://github.com/jamsinclair/jSquash/blob/main/packages/webp/README.md)).
- `@jsquash/resize` requires both width and height. Keeping aspect ratio therefore requires the caller to read the decoded dimensions and calculate each paired height; its API does not accept “width only” like Sharp ([resize README](https://github.com/jamsinclair/jSquash/blob/main/packages/resize/README.md)).
- Browser bundling is part of the integration surface. The package READMEs say codec Wasm must be included manually or through a bundler; manual `init` functions exist when automatic loading does not fit the runtime ([resize README](https://github.com/jamsinclair/jSquash/blob/main/packages/resize/README.md), [WebP README](https://github.com/jamsinclair/jSquash/blob/main/packages/webp/README.md)).
- Node support is explicitly “limited” and “experimental,” with Wasm not optimized for Node. The official Node example reads codec `.wasm` files from `node_modules`, compiles them, initializes the decoder/encoder, and then reads/writes binary files ([project README](https://github.com/jamsinclair/jSquash/blob/main/README.md), [Node example](https://github.com/jamsinclair/jSquash/blob/main/examples/with-node/index.js)). There is no first-party Bun support statement in the project documentation found here.
- Deno support has a first-party example: Deno 1.39+ reads JPEG, decodes it, WebP-encodes it, and writes a `Uint8Array` ([Deno example](https://github.com/jamsinclair/jSquash/blob/main/examples/with-deno/index.js)).
- Maintenance is not frozen: `@jsquash/resize` 2.1.1 was published in January 2026, while the latest WebP package is 1.5.0 from the owning npm package metadata ([resize npm](https://www.npmjs.com/package/@jsquash/resize), [WebP npm metadata](https://registry.npmjs.org/@jsquash%2fwebp/latest)). That makes jSquash a more credible browser-Wasm option than retired libSquoosh, but does not erase its stated server limitations.
- For this flow, client-side jSquash moves the expensive transform off the dev server, but it still needs a binary protocol to upload one or many generated files. It also changes the stated “server API converts” boundary, so it is an alternative architecture to grill, not a drop-in implementation of that exact boundary.

### 4. `wasm-vips`

- `wasm-vips` compiles libvips to WebAssembly and exposes browser, Node.js, and Deno entry points. The current npm package is 0.0.18 (June 2026), but the README still labels it early development ([npm](https://www.npmjs.com/package/wasm-vips), [README](https://github.com/kleisauke/wasm-vips/blob/master/README.md)).
- Its server API is closer to Sharp than jSquash: initialize Vips once, pass encoded bytes to `Image.thumbnailBuffer`, write WebP bytes with `writeToBuffer(".webp", { Q: quality })`, and release each image object. The maintainer recommends `thumbnailBuffer` rather than decoding then calling `thumbnailImage`, because the former can use shrink-on-load optimizations ([maintainer guidance](https://github.com/kleisauke/wasm-vips/issues/75#issuecomment-2566948407)).
- Node and Deno are documented. Browser usage requires WebAssembly SIMD, WebAssembly exception handling, `SharedArrayBuffer`, and cross-origin isolation headers (`COOP` / `COEP`) ([README](https://github.com/kleisauke/wasm-vips/blob/master/README.md)).
- Bun is the blocker: an open project issue contains the owner's December 2025 test result that Bun 1.3.5 failed with memory errors, with no later resolution recorded in that issue as of this research ([Bun issue](https://github.com/kleisauke/wasm-vips/issues/108)). It remains a viable **spike candidate**, not an evidence-backed Bun baseline.

### 5. Squoosh lineage and command-line options

- The original Squoosh application proves the browser-local model—its project README says compression happens locally and images are not sent to a server ([Squoosh README](https://github.com/GoogleChromeLabs/squoosh)). However, the reusable Node package and CLI are different artifacts from the web app.
- `@squoosh/lib` and `@squoosh/cli` were experimental even before retirement. Their own READMEs now say “Project no longer maintained,” and the owning repository removed both packages in January 2023 ([lib README](https://github.com/GoogleChromeLabs/squoosh/blob/918c596cba36a46ff3d7aa8ffd69580bd22528e2/libsquoosh/README.md), [CLI README](https://github.com/GoogleChromeLabs/squoosh/blob/918c596cba36a46ff3d7aa8ffd69580bd22528e2/cli/README.md), [removal PR](https://github.com/GoogleChromeLabs/squoosh/pull/1321)). They should inform lineage only.
- `sharp-cli` is a maintained CLI-shaped alternative over Sharp. It supports resize, forced WebP format, quality, output directories, and filename macros; v5.2.0 was released June 2025 ([README](https://github.com/vseventer/sharp-cli/blob/master/README.md), [release](https://github.com/vseventer/sharp-cli/releases/tag/v5.2.0)). It is useful for offline batch scripts, but a route would need to spawn and supervise a process, and it retains Sharp's native install requirements.

## Practical implications for the desired flow

1. **A transform library does not complete the upload feature.** The current Writer contract stores strings only ([source](../../../packages/crud/src/types.ts)). Whether transforms run in Sharp, Astro's service, wasm-vips, or jSquash, the route still needs bounded binary input, binary writes, path allowlisting, overwrite/cleanup behavior, and failure handling.
2. **Generating width files and generating a `srcset` attribute are separable.** Sharp, wasm-vips, and jSquash return/write image bytes; the CMS chooses filenames. Astro `getImage()` and the image-service `getSrcSet()` model generate transform descriptors/URLs, but Astro's documented storage target is build output rather than the authoring folder ([Astro `getImage`](https://v5.docs.astro.build/en/reference/modules/astro-assets/#getimage), [Image Service API](https://v5.docs.astro.build/en/reference/image-service-reference/)).
3. **Canonical-only YAML is compatible with every engine evaluated.** None requires derivative paths to be persisted in YAML; the mapping can be derived from a naming convention or another CMS-owned manifest. Which mechanism is stable enough is still a product question.
4. **Native vs Wasm is not simply “friction” vs “no friction.”** Sharp needs platform binaries and Node-API/lifecycle handling but provides broad prebuilds and explicit Bun/Deno support ([install](https://sharp.pixelplumbing.com/install/)). jSquash needs codec-specific Wasm loading and `ImageData` plumbing ([project README](https://github.com/jamsinclair/jSquash/blob/main/README.md)); wasm-vips browser use needs cross-origin isolation and its Bun status is unresolved ([README](https://github.com/kleisauke/wasm-vips/blob/master/README.md), [Bun issue](https://github.com/kleisauke/wasm-vips/issues/108)).
5. **Input limits matter regardless of engine.** Sharp exposes `limitInputPixels`, and Astro forwards this option to its Sharp service ([Sharp constructor](https://sharp.pixelplumbing.com/api-constructor/), [Astro Sharp service](https://github.com/withastro/astro/blob/main/packages/astro/src/assets/services/sharp.ts)). Upload byte limits, allowed source formats, animated-image behavior, and SVG policy remain API decisions.

## Open questions for the grill

1. Is the canonical `cover.webp` an unscaled WebP conversion, the largest configured width, or a separately bounded “master”?
2. What default widths, WebP quality/effort, no-upscale behavior, and filename convention are required for the demo?
3. Is the original upload retained beside derivatives, replaced by WebP, or discarded after a successful transaction?
4. Should authored `srcset` URLs be derived from deterministic filenames, read from a generated manifest, or exposed through a wrapper around Astro `<Image>`? Astro's own `srcset` URLs target its image service/build artifacts, not these beside-content derivatives ([Astro assets reference](https://v5.docs.astro.build/en/reference/modules/astro-assets/#getimage)).
5. Should the CMS call `sharp` directly, or deliberately reuse the host's configured Astro local image service so authoring and render-time encoder settings track each other?
6. Is Deno parity required for this first binary route? If yes, are Sharp's local `node_modules`, FFI, environment, read, write, and system permissions acceptable ([Sharp install](https://sharp.pixelplumbing.com/install/), [Deno example](https://docs.deno.com/examples/resize_images/))?
7. Does “browser Wasm” remain a desired fallback? If yes, does the browser upload only derivatives or also the original, and how are partial multi-file writes rolled back?
8. Which formats and edge cases are in scope: JPEG/PNG/WebP only, EXIF orientation, transparency, animated GIF/WebP, SVG rasterization, and metadata retention?
